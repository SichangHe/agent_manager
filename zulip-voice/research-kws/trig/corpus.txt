What we were asked, what we did, and why
(authored by agents unless marked 🧑)

 Step 1. The project in one paragraph

Cloud games stream the whole screen as video. Small text blurs and every pixel costs bandwidth. The project's idea: stream only the game world as video, and send the UI as a small description that the player's device redraws with the game's own fonts and art. The owner built a "UI client" for three Unity games that does this, and showed it draws the UI pixel-exactly for the states they tested (29, 40 and 30 states).

 Step 2. The weakness the owner found

"Pixel-exact" only means something for the UI states that were actually tested. The owner's own coverage benchmark showed the tests touched only 20%, 48% and 9% of each game's UI elements. Their AI agents, playing by screenshots, "reportedly get stuck playing the game". So fidelity was proven for a small slice of the UI.

 Step 3. What we were asked

The human's words: "The task is to explore as much UI state as possible and show our fidelity." The game world only matters because certain UI appears only in certain world states (a battle HUD needs a battle). The human suggested constructing such states directly through the game's inspector instead of playing there, while keeping the game logic valid.

So the goal has two parts:
- reach as much of the UI as possible
- prove the client draws all of it pixel-exactly

 Step 4. The first problem: what does "as much as possible" mean?

A coverage percentage needs a total. The owner's total is "every UI panel listed in the game's files". We found that this total is badly inflated: a large part of those panels can never appear, because no game code ever turns them on. Example: 348 of Unchained's 454 panels; 338 of them belong to one old combat screen that nothing in the game uses. So "9% coverage" on Unchained mostly measured leftover files, not weak exploration.

We also checked the research literature (Android apps, web, fuzzing). Nobody can count all UI states of a program exactly; the best methods either list possible pieces or estimate totals statistically, and the statistical estimates only describe what one explorer could find.

 Step 5. Our fix for the total: static analysis

We wrote a tool that reads the game's code and asks, for each listed panel: is there any line of code that can make it visible? (turning it on, fading it in, spawning it, loading its scene, calling it by name from a button.) Panels with such code are "showable"; the rest are excluded, with the evidence listed.

- It is fast (seconds to minutes per game, one CPU, no AI) because it does not simulate the game; it only checks that such code exists.
- It errs on the generous side: any code that can show a panel counts, even if play might never reach it. So it never shrinks the total unfairly.
- Validation: every panel that any explorer actually saw on screen is marked showable (126 of 126 across two games). Hand checks of random samples found the labels correct.

Result: Spurpunk has about 175 showable panels (of 180 listed); Unchained about 104 (of 454). Explorers already reach about a quarter of Unchained's showable UI, not 6%.

 Step 6. Reaching more UI

We compare five ways of exploring, each with the same time limit:
1. random clicking (a floor)
2. the owner's screenshot agent
3. the owner's agent that also reads the live list of buttons
4. ours: scripts call the game's own code to jump into deep states (start a battle, open a shop), then click around
5. ours: those scripts, then an agent explores from the deep state

First results (10 minutes): scripting reaches more panels on the two harder games and fewer on the easy one; no decisive winner yet. Longer runs and methods 3 and 5 are running now. Next, the static analysis will also tell the scripts which code to trigger to reach each unreached panel, so state construction becomes systematic instead of hand-written.

 Step 7. Proving fidelity on the new states

Every state any method reaches is replayed through the client and compared pixel by pixel with the real game. Deeper exploration already paid off: it found 7 real cases where the client drew slightly wrong pixels (a wrong animation frame, text at 99.996% instead of 100% opacity, a missing particle effect, and others). All 7 are fixed and submitted to the owner as a pull request.

 Step 8. What the paper will say

"Our client is pixel-exact on X% of each game's showable UI", where:
- "showable" comes from the static analysis (Step 5), validated against everything seen at runtime
- X comes from the best exploration method (Step 6)
- pixel-exact comes from comparing every reached state (Step 7)

 Why this approach

- Playing alone gets stuck, so we jump into deep states using the game's own code (the human's inspector idea), which keeps game logic valid.
- A percentage needs an honest total, and the file list is not one; the static analysis gives a total we can defend without claiming to know every state.
- We kept the claims to what we can check: the analysis says which panels have code that can show them, not which ones players will see; exploration measures the latter.

A batch sends several browser actions in one model call. Scripts additionally loop and make conditional decisions. Likely, these tasks often need only batching, but that cause is unproven. The clearest measured problem is output delivery: the controller discards script output after 16,000 characters. Asking for another output page cannot recover it. Summary
The paper measures how often Hugging Face model cards (809,703 cards) contain substantive safety disclosure, and asks whether the download-weighted rate exceeds the unweighted rate by at least 15 percentage points. On the authors' chosen estimator the gap is -2.9 pp, so the hypothesis is rejected. Secondary results: a row-level download-weighted gap of +11.21 pp that depends on a few models, and frequent licence omission in derived models (44.21% of edges).

Strengths
1. Large, registry-wide data set, including 48,247 derivation edges.
2. The paper reports negative results and sensitivity analyses (e.g., trimming the top ten models) openly.
3. Licence omission in derivatives is a concrete, practically relevant observation.

Weaknesses
1. Unclear motivation and contribution (major). The abstract and introduction do not explain why a +15 pp difference between weighted and unweighted disclosure rates would matter for Web systems or governance, or what anyone should do differently given the answer. The threshold appears arbitrary. Please state the decision this measurement informs.
2. Measurement validity (major, undermines all rates). Safety levels come from a keyword extractor whose L2 precision is 44.00% (33/75) on the 300-card validation sample (Fig. 1, stage 3). With more than half of positive labels wrong, the reported rates are not interpretable: the paper's own precision-only correction moves the overall rate from 27.19% to 9.74-15.52%, yet the headline gap (H2) is computed on uncorrected labels. A validated classifier, or applying the correction to the weighted and unweighted rates alike, would address this.
3. "Registration" after data access (major). The hypotheses were "registered after data access" (Abstract), so the confirmatory framing (registered margins, falsification verdicts) does not carry its usual meaning. Much of the text is spent on this framing, which makes the paper hard to follow. Presenting the study as exploratory and plainly would be more accurate and more readable.
4. Readability (moderate). Nearly every sentence carries qualifiers about which estimator is registered or unregistered. A reader cannot extract the aims and conclusions from the abstract alone.

Questions for the authors
1. What decision or policy depends on whether the gap exceeds 15 pp, and why 15? (W1)
2. Does the H2 gap survive when the precision correction is applied to both the weighted and unweighted rates? (W2)
3. What, concretely, was fixed before data access? (W3)

Summary
The paper looks at model cards on Hugging Face and asks whether popular models (weighted by downloads) document safety better than the average model. The answer seems to be no, or maybe, depending on how it is computed.

Strengths
1. The data set is large and covers most of the Hub.
2. The authors report negative results honestly.
3. The observation that a few hugely popular models dominate any download-weighted number is useful, though it is buried as a side point.

Weaknesses
1. I don't see the point. After the abstract and introduction I still could not tell why this question matters. If popular models turned out to document safety a bit better or worse, what would anyone do differently? Why is 15 percentage points the line that matters? The question feels narrow, and the paper does not explain why the Web community should care about the answer.
2. The measurement is not reliable. Safety text is detected by keyword matching, and by the authors' own check it is wrong more often than right (44% precision). With that, I don't trust the reported rates or the differences between them.
3. The results don't settle anything. The main hypothesis comes out negative on one estimate, inconclusive on another, and the effect mostly disappears when ten models are removed. I came away with no conclusion I could use. The "registered hypotheses" framing also doesn't help, since the paper says they were registered after the authors had already seen the data.
4. Readability is very bad. Nearly every sentence is wrapped in qualifiers about which estimator or test is meant. What is in effect a simple counting question is presented in a way that makes it very hard to understand what was done and what was found.

Questions for the authors
1. What is the point? Concretely, what decision or practice would change depending on your answer?

Overall: reject. The motivation is missing, the measurement can't support the conclusions, and the writing hides a simple study behind heavy jargon.

ABOUT THE ENGINE

1. JIT side effects (V8, SpiderMonkey)
- failure: CVE-2020-6418, exploited in the wild: the JIT assumed an operation had no side effects, but a Proxy could run code and change an array's type
- prove: any operation that may run JS invalidates the type facts the JIT inferred before it
- tried: a solver model catches the CVE's bug shape; model only

2. JIT range analysis (V8)
- failure: CVE-2021-21220: the JIT wrongly concluded a value is always 0 and removed a bounds check
- prove: the range the JIT computes for each operation contains every real result
- tried: a solver checked V8's integer range rules; multiplication could not be settled at 64 bits; model only

3. JIT phases keep earlier decisions valid (V8)
- failure: CVE-2021-4102: a later phase changed a value after an earlier phase decided a memory-write safety check was unnecessary
- prove: decisions made in an earlier phase stay true after later phases
- tried: toy proof; an independent review says it is a related but different bug

4. Garbage collector frees only dead objects (V8, Boa)
- failure: CVE-2021-37975, exploited in the wild: live objects stayed unmarked and were freed
- prove: when sweeping starts, every reachable object is marked
- tried: proofs of Boa's marking algorithm (model); found a real Boa use-after-free (an object revived by its finalizer is freed anyway), confirmed twice

5. Sandboxed code stays in its memory (Wasmtime, V8 sandbox)
- failure: CVE-2023-26489: Wasmtime computed 35-bit addresses where 33 were allowed, reaching outside the sandbox
- prove: every memory access an attacker can steer lands inside its own region
- tried: proofs on models of Wasm bounds checks and V8's pointer table; the CVE's bug is rejected

6. Tabs or tenants sharing one process cannot reach each other
- failure: vm2 CVE-2023-29017: sandboxed code got a host object and escaped
- prove: no object of context A is reachable from context B except through declared channels (Spectre out of scope)
- tried: proof on a two-context heap model, for any sequence of operations

7. URL parser follows the standard (rust-url, used by Servo)
- failure: parsers disagreeing on the same URL is a known attack source
- prove: for every input the parser gives the WHATWG standard's result
- tried: rust-url fails 69 of 896 standard tests; a proof pinned one bug class (Windows drive letters) that also crashes debug builds; two of its bugs were already reported upstream

8. Cleaned HTML stays clean (DOMPurify, ammonia)
- failure: DOMPurify CVE-2024-47875: cleaned HTML turned into script after being parsed again

- tried: ammonia's default settings stay script-free but are not a stable round trip; a non-default setting allowed real script injection

9. Event loop runs callbacks in the standard's order (Boa, Node)
- failure: Node 10 and earlier ran timers before promise callbacks

Direct answers (from two research reports; "opinion" marks judgment):

Do we need to verify the JS engine to share processes?
No, not the whole engine (opinion). What must hold is a short list: each tenant's heap stays separate; JIT code stays in its tenant's memory and cannot change memory protection or jump anywhere; code outside the sandbox treats every value from inside as untrusted. Spectre needs separate handling. V8's own sandbox already assumes "an attacker can arbitrarily ... modify any memory inside the sandbox", so isolation is designed not to need a correct engine.

Can we verify C++ engines? Can we verify enough?
Not fully. The biggest verified C is seL4: 8,700 lines of C, 200,000 lines of proof. Engines are 10-100x bigger, and no verified C++ near that size exists. "Enough" is possible only for the isolation boundary: the sandbox edge and the machine code the JIT emits.

Is Servo a good target? An agent browser on Servo?
Best Rust option, but Verus reaches only small parts: Servo is a prototype (577k lines of Rust), and its JS engine is SpiderMonkey, in C++; two thirds of its unsafe Rust is glue to that engine. Opinion: build a small Verus-verified Rust core (session isolation, request policy, cookies, origins) and treat Servo as an untrusted page renderer under it. Unknown: Servo's current web-compatibility level, and whether it speaks the protocol agents use (CDP).

Why is Lightpanda efficient?
Mostly by leaving things out: no page rendering, no Chrome multi-process design, one process with one thread and one V8 instance per connection, pooled memory. Its "9x faster" compares 25 Lightpanda processes to 25 tabs in one Chrome; one-to-one it is about 1.6x faster with about 48x less memory, on the vendor's own single demo site.

A new verified JIT at state-of-the-art speed?
Not workable as stated: no verified JS engine or JIT exists, and verified compilers still trail unverified ones (CompCert was ~7-12% slower than gcc -O1/-O2). Realistic slices: verify one JIT component inside a real engine (Icarus, SOSP 2024, did SpiderMonkey's inline-cache code with no slowdown), or check each piece of JIT output before it runs.

Explicit side effects with monads?

On-the-fly verification of page JavaScript: is it legit?

Short answer (opinion): yes as an idea, with strong precedent; unproven for real JavaScript; that gap is the research.

Why it is legit:
- checking untrusted code right before running it is an established systems idea: proof-carrying code (Necula, 1997), Google Native Client's validator, the Linux kernel's eBPF verifier (runs on every program loaded, in production), VeriWasm for WebAssembly
- browsers already do a weak version: JIT engines assume facts about the current page state and undo optimizations when those facts change
- our earlier search found no system that proves a property of a page's scripts for the current page state and drops the proof when that state changes (searches only, not proof of absence)

Why it is hard:
- those precedents verify small, restricted code (eBPF limits loops and size); page JavaScript is large, dynamic (eval, prototypes changed at run time: 63 of 95 real sites changed a built-in after load) and arrives in pieces
- the property must be decided in milliseconds during page load
- our own prototype was a toy: the first version was unsound; the fixed one works only on a tiny JavaScript subset

What it could look like (opinion): an eBPF-style verifier for the web: a page's scripts get a fast load-time check of a narrow property (e.g. "never reads the password field and sends it elsewhere", or "stays inside its tab's heap" for process sharing), and the browser falls back to today's isolation when the check fails or the state changes.

I'll have this dug into properly: prior work, how much real page JS such a checker could cover, and what property is both useful and checkable fast.

PART 2. Pitches and weirder ideas
Project pitches for your advisors (opinions; each built around one real failure, one guarantee we prove, the closest prior work, and a first paper):

A. Certified JavaScript rewrites for web-archive replay (fits Harsha's archive work)
- failure: archives rewrite each page's JS so it replays offline; wrong rewrites break pages. FidEx (NSDI 2026, Madhyastha's group) cut broken replays "from 15% to 9%", so 9% still fail; agent benchmarks now run on archives
- prove: a checker that, when it accepts a rewrite, guarantees original and rewritten code behave the same for this page's actual state (exactly the advisors' "for the given state" remark)
- new: FidEx finds errors by comparing two runs; this certifies a rewrite without them
- first paper (~4-6 months): checker for the most common rewrite family; evaluate on FidEx's historical failures. First 2 weeks: classify FidEx failures, continue only if many fit one small model
- risk: getters and dynamic state may make most real rewrites uncheckable

B. A verified request/session core for agent browsers
- failure: 9 of Lightpanda's 11 security bugs, plus our WebSocket finding, are in rules for URLs, cookies, redirects and control access
- prove (Verus, Rust): every connection is checked; origins follow the URL standard; cookies go only where allowed; session A never sees session B's data; only the owner controls a session. Engine stays untrusted
- new: the last verified browser core was Quark (2012), one process per tab, before agents and modern cookie rules; 2026 agent-security papers use labels/guardrails, none verifies browser code
- first paper (~4-5 months): Verus core attached to Servo; show every Lightpanda rule bug becomes impossible; measure cost with many sessions
- risk: reviewers call it "a verified firewall"; an engine memory bug still breaks isolation

C. Checking JIT output so tenants can share a process (your tab-sharing idea)
- failure: Cloudflare runs tenants in one process and says code that can run arbitrary machine code "could disable memory protection keys"; its 2026 Spectre demo leaked 12 bit/s in production
- prove: each piece of JIT code, before it runs, only touches its tenant's memory and jumps only to allowed places
- new: Icarus verifies JIT generators once; Mohabi separates the whole engine from the browser; VeriWasm/LFI check fixed code; nobody checks many tenants inside one JS JIT (abstract-level search)
- first paper (~6-9 months after a 4-week feasibility gate)
- risk: most crowded (the UCSD/Stanford group owns this space) and Spectre is not covered

Ranking (opinion): A best group fit, B smallest and clearest, C riskiest.

Weirder ideas, mined from your past work (one line each; "no hit" = one Scholar page only):
1. security facts that must never roll back when the browser restores old state (back button cache, session restore, archive replay): e.g. "logged out" stays logged out; no hit
